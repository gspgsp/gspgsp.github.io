一、先建立整体框架

Kubernetes（简称 K8s）本质上是一个容器编排系统：你告诉它"我想要什么状态"（比如"我要3个副本一直运行"），它负责持续地把实际状态调整到你想要的状态，这叫声明式（declarative）管理，是理解一切的基础。

五个概念可以分成三类：

分类概念本质
环境Minikube提供一个可以运行 K8s 的地方（本地集群）
工具kubectl用来和集群沟通的客户端
资源对象（Kubernetes API 里定义的"东西"）Pod运行容器的最小单元
Deployment管理一组 Pod 的控制器
Service给 Pod 提供固定网络入口的抽象

记住这句话就理解了 80%：Minikube 是地，kubectl 是嘴，Pod/Deployment/Service 都是活在这块地上的、通过嘴巴创造和管理的"东西"（资源对象）。

二、Minikube：本地集群

是什么

一个完整的 Kubernetes 集群，在生产环境中通常由多台机器组成：

  • 一个或多个 Master 节点（控制平面）：负责调度、决策，包含 API Server、etcd（存储集群状态的数据库）、Scheduler（调度器）、Controller Manager（各种控制器的大脑）。
  • 若干个 Worker 节点：真正运行你容器的机器。

Minikube 做的事情：把这一整套东西压缩进你本地的一台虚拟机或容器里，让你不需要买云服务器就能体验和学习真实的 K8s 集群行为。它是一个单节点集群（Master 和 Worker 合二为一），只用于开发/测试，不能用于生产。

类比

如果把 Kubernetes 集群比作一座"机场"：

  • 真实生产集群 = 一座有多个跑道、多个航站楼的大型国际机场
  • Minikube = 你在自家后院搭的一个迷你模拟机场，五脏俱全，但只能起降玩具飞机

常用命令

minikube start              # 启动本地集群（首次会下载镜像，稍慢）
minikube status             # 查看集群运行状态
minikube stop                # 停止集群（不删除数据）
minikube delete              # 彻底删除集群
minikube dashboard           # 打开图形化管理界面
minikube ip                  # 查看集群节点的IP

它和真实集群的区别

除了"单节点"和"仅供本地使用"之外，行为逻辑、YAML 写法、kubectl 命令完全一致。这也是它存在的意义——你在 Minikube 上学会的一切，直接搬到云上的真实集群（比如阿里云 ACK、AWS EKS、GKE）也是通用的。

三、kubectl：命令行客户端

是什么

kubectl（读作 "kube control" 或 "kube cuttle"）是一个命令行工具，它本身不是集群的一部分，而是运行在你本地电脑上，负责把你的指令翻译成 HTTP 请求，发送给集群的 API Server。

你敲命令
   │
   ▼
kubectl (把命令转成 REST API 请求)
   │
   ▼
API Server (集群的唯一入口，所有操作都要经过它)
   │
   ▼
etcd (真正存储集群状态的数据库) + 各种控制器读取状态并采取行动

也就是说，kubectl 从不直接操作 Pod 或容器，它只是"发请求给 API Server，说我想要什么状态"，剩下的事情由集群内部的各种控制器自动完成。

两种最核心的使用方式

1. 命令式（imperative）—— 直接敲命令

kubectl run mypod --image=nginx
kubectl create deployment myapp --image=nginx --replicas=3

适合临时测试，但不方便版本管理和复现。

2. 声明式（declarative）—— 写 YAML 文件，让 kubectl 去"对齐"这个状态

kubectl apply -f deployment.yaml

这是生产环境的标准做法：YAML 文件描述"最终应该是什么样子"，可以纳入 Git 做版本管理，团队协作、CI/CD 都基于这种方式。apply 是幂等的——反复执行同一个文件，只有状态和文件不一致时才会真正改变集群。

常用命令分类记忆

# 查看类
kubectl get pods / deployments / services / nodes
kubectl describe pod <name>       # 看详细信息，排错第一步
kubectl logs <pod-name>            # 看容器日志

# 操作类
kubectl apply -f xxx.yaml          # 创建或更新资源
kubectl delete -f xxx.yaml         # 删除资源
kubectl scale deployment xxx --replicas=5

# 进入容器
kubectl exec -it <pod-name> -- /bin/sh

四、Pod：最小调度单元

是什么

Pod 是 Kubernetes 中能够被创建和调度的最小单位。注意，Kubernetes 不直接管理容器，而是管理 Pod——Pod 是对一个或多个容器的一层封装。

一个 Pod 内的所有容器：

  • 共享同一个网络命名空间（同一个 IP、可以用 localhost互相通信）
  • 可以共享存储卷（Volume）
  • 总是被一起调度到同一台节点，一起创建、一起销毁

为什么需要这层封装，而不是直接管理容器？

因为很多场景需要"一组容器绑在一起工作"。经典例子是 sidecar 模式：主容器负责业务逻辑，另一个小容器负责日志采集或者反向代理，它们需要共享网络和文件系统，被当作一个整体来调度和维护。

apiVersion: v1
kind: Pod
metadata:
  name: example-pod
  labels:
    app: my-app          # label 非常重要，后面 Service/Deployment 靠它识别 Pod
spec:
  containers:
  - name: main-container
    image: nginx:1.25
    ports:
    - containerPort: 80
  - name: sidecar-logger
    image: busybox
    command: ["sh", "-c", "tail -f /var/log/nginx/access.log"]

Pod 的关键特性：短暂（ephemeral）

这是理解后面 Deployment 和 Service 为什么存在的关键：

  • Pod 随时可能死掉：节点故障、资源不足被驱逐、镜像更新……
  • Pod 死掉后不会被"复活"，而是由上层控制器（比如 Deployment）创建一个全新的 Pod 来代替它。
  • 新 Pod 的 IP 地址会变化——这意味着你永远不应该硬编码 Pod 的 IP 去访问它。

正因为 Pod 如此"脆弱易变"，实际使用中你几乎不会直接创建 Pod，而是通过 Deployment（或 StatefulSet、DaemonSet 等其他控制器）来间接管理它们。

五、Deployment：Pod 的管理者

是什么

Deployment 是一个控制器（Controller），它的职责是：持续监控并维持一组 Pod 处于你声明的期望状态。

这是 Kubernetes "控制循环（Control Loop）"思想的典型体现：

期望状态（你写的 YAML：我要3个副本）
        │
        ▼
   Controller 不断对比
        │
   实际状态 ≠ 期望状态？
        │
        ▼ 是
   自动采取行动，让实际状态趋近期望状态
   （创建/删除/替换 Pod）
        │
        ▼ 否
   什么都不做，继续监控（循环往复，永不停止）

Deployment 具体解决了三个问题

1. 保证副本数量（自愈能力）

你说"我要 3 个 Pod"，如果某个 Pod 因为任何原因挂了，Deployment 会立刻发现"实际只剩2个了"，自动创建一个新的补上。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:                    # 这部分是 Pod 的模板，Deployment 靠这个模板去"复制"Pod
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80

2. 滚动更新（Rolling Update）不中断服务

当你把镜像版本改成 nginx:1.26 再执行 kubectl apply，Deployment 不会一次性把 3 个 Pod 全杀掉重建（那样服务会中断），而是：

先创建1个新版本Pod → 等它就绪 → 删除1个旧版本Pod
      → 再创建1个新版本Pod → 等它就绪 → 删除1个旧版本Pod
            → 重复直到全部替换完成

整个过程中始终有 Pod 在正常提供服务，这就是零停机更新的原理。

kubectl set image deployment/nginx-deployment nginx=nginx:1.26
kubectl rollout status deployment/nginx-deployment    # 查看更新进度
kubectl rollout undo deployment/nginx-deployment       # 一键回滚到上一版本

3. 弹性伸缩

kubectl scale deployment nginx-deployment --replicas=10

一条命令，Deployment 会立刻创建/删除 Pod 来匹配新的副本数。

Deployment 与 Pod 的从属关系（重要，容易忽略的细节）

实际上 Deployment 并不直接管理 Pod，中间还隔着一层 ReplicaSet：

Deployment  ──创建/管理──►  ReplicaSet  ──创建/管理──►  Pod × N
（负责版本、滚动更新策略）    （负责保证某一版本Pod的数量正确）

每次滚动更新，Deployment 会创建一个新的 ReplicaSet（对应新版本），逐步把 Pod 从旧 ReplicaSet 挪到新 ReplicaSet，旧的 ReplicaSet 会被缩容到 0（但保留记录，方便回滚）。日常使用中这层细节可以先不深究，但排错时如果看到 kubectl get rs 输出了很多 ReplicaSet，不用惊讶。

六、Service：稳定的网络入口

要解决的问题

前面说过，Pod 的 IP 会随时变化（重建、扩缩容都会导致 IP 变化）。假设你的前端要访问后端的 3 个 Pod，如果直接记录这 3 个 IP，那么：

  • Pod 重启后 IP 变了，前端记录的地址失效
  • 扩容出的新 Pod，前端根本不知道它的存在
  • 3 个 Pod 之间如何做负载均衡，前端也得自己实现

Service 就是用来解决这个问题的一层网络抽象：它提供一个固定不变的虚拟 IP（ClusterIP）和 DNS 名称，自动帮你找到所有匹配的、健康的 Pod，并做负载均衡转发。

核心机制：Label Selector

Service 从不关心 Pod 是谁创建的、叫什么名字，它只通过 标签选择器（Label Selector） 来匹配 Pod：

apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx          # 只要 Pod 身上贴着 app=nginx 这个标签，就会被自动纳入
  ports:
    - protocol: TCP
      port: 80            # Service 自己对外暴露的端口
      targetPort: 80       # 转发到 Pod 容器内部监听的端口

这就是为什么前面 Deployment 的 Pod 模板里一定要写 labels: app: nginx——Service 靠这个标签才能找到它们。这个匹配关系是动态实时的：Pod 增加了自动被纳入，Pod 减少了自动被移出，完全不需要人工维护列表。

              labels: app=nginx
Service ────────────────────────┐
(固定虚拟IP/域名)                 │ 自动发现、持续追踪
                                 ▼
                    ┌─────┬─────┬─────┬─────┐
                    Pod1  Pod2  Pod3  Pod4(新扩容出来的，自动被纳入)

Service 的几种类型

类型作用范围使用场景
ClusterIP（默认）仅集群内部可访问微服务之间互相调用，比如前端调后端
NodePort通过 节点IP:固定端口 从集群外部访问本地开发测试（Minikube 常用）
LoadBalancer由云厂商分配一个公网负载均衡器生产环境，直接对公网提供服务
ExternalName把 Service 映射到一个外部 DNS 名称集群内访问集群外的服务，比如外部数据库

在 Minikube 上暴露服务，通常这样做：

minikube service nginx-service   # 自动找到 NodePort，直接帮你打开浏览器访问

Service 还提供内部 DNS

Kubernetes 集群内置了 DNS 解析（CoreDNS），任何 Pod 都可以直接用 Service 的名字访问它，不需要知道 IP：

http://nginx-service.default.svc.cluster.local

或者更简单，同一个命名空间内直接用 nginx-service 这个名字即可，DNS 会自动解析。

八、一次请求的完整链路

以"用户访问一个 Web 服务"为例，从头到尾走一遍：

  1. 搭建阶段：minikube start 启动本地集群。
  2. 部署阶段：编写 deployment.yaml 并 kubectl apply -f deployment.yaml
    • API Server 收到请求，把"我要3个带 app=web 标签的Pod"这个期望状态存入 etcd
    • Deployment 控制器发现期望状态与实际不符（当前0个），创建 3 个 Pod
    • Kubernetes 的调度器（Scheduler）决定每个 Pod 具体跑在哪个节点上
  3. 暴露服务阶段：编写 service.yaml 并 kubectl apply -f service.yaml
    • Service 被创建，它持续监听所有带 app=web 标签的 Pod，自动把它们纳入自己的转发列表
  4. 请求阶段：用户发起一个 HTTP 请求
    • 请求先到达 Service 的固定入口（NodePort 或 LoadBalancer）
    • Service 根据内部的负载均衡规则，随机/轮询选择一个健康的 Pod
    • 请求被转发到该 Pod 内的容器，容器处理并返回响应
  5. 运维阶段：某天你更新了代码，重新打包镜像为 v2
    • 执行 kubectl set image deployment/web-deploy web=myimage:v2
    • Deployment 触发滚动更新：逐个替换 Pod，期间 Service 始终能找到"当前存活"的 Pod 来转发流量，用户全程无感知
  6. 故障恢复：某个 Pod 所在节点突然宕机
    • Deployment 控制器发现实际 Pod 数量少了，自动在健康节点上创建新 Pod 补齐
    • 新 Pod 启动后自动带着相同的 label，被 Service 自动重新纳入转发列表

九、常用命令速查表

# ── 集群管理 ──
minikube start / stop / delete / status
minikube dashboard              # 图形化界面

# ── 查看资源 ──

# ── 创建与更新 ──

kubectl rollout undo deployment/<name>        # 回滚上一版本
kubectl rollout history deployment/<name>     # 查看历史版本

十、常见误区

误区1：以为 kubectl 直接操作容器 实际上 kubectl 只是把你的意图告诉 API Server，真正执行创建/销毁容器的是节点上的 kubelet 组件，整个链条是 kubectl → API Server → 调度器/控制器 → kubelet → 容器运行时（如 containerd）。

误区2：把 Pod 当成"虚拟机"一样长期维护 不要往 Pod 里手动装东西、改配置后期望它一直存在——Pod 应该被当作随时可丢弃、可重建的对象，所有持久化的东西（数据、配置）应该用 Volume、ConfigMap、Secret 等独立资源管理，而不是依赖某个具体 Pod 的存活。

误区3：认为 Service 是一种"负载均衡服务器"实体 Service 更准确地说是一条iptables/IPVS 转发规则（由每个节点上的 kube-proxy 组件维护），并不是一个真实运行着的负载均衡进程。它是一层"抽象"，而非"实体"。

误区4：混淆 Deployment 和 Pod 的数量关系 一个 Deployment 通常对应多个 Pod（由 replicas 决定），不要以为一个 Deployment 只管理一个 Pod。

误区5：以为 Minikube 上学的东西换个云平台就不适用了 恰恰相反，Kubernetes 的核心设计目标之一就是"一致性"——你在 Minikube 写的 YAML，理论上原封不动地 apply 到阿里云/AWS 的真实集群上也能跑起来（网络细节、存储类等可能需要适配，但核心概念和命令完全通用）。

细节分析1

Service 下的 NodePort 和 Port 的关系

先搞清楚 Service 身上其实同时挂着好几个"端口"

一个 NodePort 类型的 Service,YAML 大概长这样:

apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: NodePort
  selector:
    app: nginx
  ports:
    - port: 80          # Service 自己的虚拟IP(ClusterIP)上监听的端口
      targetPort: 80     # 转发到 Pod 容器内部的端口
      nodePort: 30080     # 在每个节点物理机上额外开的端口(30000-32767范围)

这里其实定义了三个端口,它们是同一条转发链路上的三个"接力点",而不是三个独立的东西:

外部用户
   │
   │ 访问 <任意节点IP>:30080  ← nodePort
   ▼
节点上的 kube-proxy 拦截这个端口的流量
   │
   │ 转发给 Service 的 ClusterIP:80   ← port
   ▼
Service (虚拟IP,不是真机器)
   │
   │ 通过 label selector 找到健康的 Pod,再转发给
   │ 某个 Pod_IP:80              ← targetPort
   ▼
Pod 里的容器,真正处理请求

关键点:NodePort 不是一个独立的组件,它是 Service 的"外部延伸"

所以准确的说法应该是:

请求先打到节点的 NodePort 端口,这个端口本质上是 Service 在每台节点上开的一个"传送门"——由每个节点上运行的 kube-proxy 组件监听并接管,kube-proxy 会把流量透明地转发到 Service 的 ClusterIP 上,然后 Service 再按照 label selector 转发给某个具体的 Pod。

用大楼类比会更直观:

  • Service (ClusterIP) 像是大楼里的"总机分机号",只有楼内的人(集群内部)才能直接拨打
  • NodePort 相当于物业在每一栋楼的大门口都装了一个对讲机,外部访客按这个对讲机的按钮(比如 30080),背后自动帮你转接到总机分机号,再由总机转给具体房间(Pod)

也就是说 NodePort 本来就是 Service 的一部分配置,不存在"先到 NodePort 再到 Service"这种物理上分离的两跳感觉——更准确的理解是"通过 NodePort 这个入口进入 Service",是同一个 Service 对象在网络层面呈现出来的两个不同"面孔"(一个对内 ClusterIP,一个对外 NodePort),背后都由 kube-proxy 统一维护的转发规则(iptables/ipvs)来实现。

在 Minikube 里你可以实际验证这个链路:

kubectl get svc nginx-service
# 会看到类似这样的输出:
# NAME            TYPE       CLUSTER-IP     PORT(S)
# nginx-service   NodePort   10.96.xx.xx    80:30080/TCP
#                                            ↑    ↑
#                                          port  nodePort

80:30080/TCP 这一行其实就已经把"Service 内部端口"和"外部 NodePort"绑定关系直接打印出来了——它们从头到尾都是同一个 Service 对象身上的两个端口而已。

细节分析2

Service 下的 Type 不同，对应的端口配置也不同

对,type 一共有 4 种可选值,而且确实每种类型能用的端口字段不一样,你这个观察很准。我按类型拆开讲清楚。

四种类型 + 各自的端口字段

类型porttargetPortnodePort额外字段
ClusterIP(默认)✓✓✗ 没有—
NodePort✓✓✓ 可选(不写会随机分配)—
LoadBalancer✓✓✓ 可选(内部依然会用到)云厂商分配的外部IP
ExternalName✗✗✗externalName

下面逐个看。

1. ClusterIP —— 只有内部两个端口,没有 nodePort

spec:
  type: ClusterIP        # 不写 type 时,这是默认值
  selector:
    app: nginx
  ports:
    - port: 80            # Service虚拟IP上监听的端口
      targetPort: 80       # 转发到Pod容器内部的端口

这种类型只能在集群内部访问(比如你的后端服务只给同集群的前端调用,不需要对外),所以完全不需要 nodePort,写了也会被忽略。

2. NodePort —— 在 ClusterIP 基础上多开一个对外端口

spec:
  type: NodePort
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080      # 可以不写,不写的话K8s会在30000-32767范围内随机分配一个

注意 NodePort 类型本身包含了 ClusterIP 的能力——它不是"取代"ClusterIP,而是"在 ClusterIP 之上多加了一个对外端口"。所以一个 NodePort 类型的 Service,集群内部依然可以用 port 那个端口访问,外部则多了 nodePort 这条路。

3. LoadBalancer —— 在 NodePort 基础上再加一层云厂商的负载均衡器

spec:
  type: LoadBalancer
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080      # 依然可以指定,云厂商LB内部还是会通过NodePort转发

这是一层"套娃"关系:

外部用户
   │
   ▼
云厂商的负载均衡器(有一个独立的公网IP,这个是LoadBalancer类型独有的)
   │
   ▼
背后自动转发到集群里某个节点的 NodePort
   │
   ▼
NodePort → Service(ClusterIP) → Pod

也就是说 LoadBalancer 类型同时具备了 ClusterIP + NodePort 的所有能力,只是额外多了云厂商分配的公网入口,用户不需要自己拼节点 IP,直接访问云厂商给的固定公网地址/域名即可。

注意:这个类型依赖云平台支持(阿里云、AWS、GCP 等),在 Minikube 这种本地环境里默认没有真实云负载均衡器可用,不过 Minikube 提供了一个变通方案:

minikube tunnel      # 模拟一个本地的LoadBalancer,让type: LoadBalancer也能在本地跑通

4. ExternalName —— 一个特殊分支,完全不涉及 Pod 转发

spec:
  type: ExternalName
  externalName: my-database.rds.amazonaws.com    # 直接映射到一个外部域名

这个类型比较特殊:它不需要 selector,不需要 port/targetPort/nodePort,因为它压根不转发流量给 Pod,只是单纯做一个 DNS 别名映射——集群内部访问这个 Service 名字时,直接被解析成外部的那个域名。常用于集群内的应用需要访问一个集群外部的服务(比如云厂商托管的数据库),又想统一用 K8s 内部的服务发现方式来调用。

一张图总结包含关系

ExternalName  ─── 完全独立,只做DNS映射,不转发流量

ClusterIP     ─── 基础能力:虚拟IP + 端口转发(集群内)
    │
    ▼ 在此基础上加一个节点端口
NodePort      ─── ClusterIP能力 + 每个节点开放的对外端口
    │
    ▼ 在此基础上再加云厂商负载均衡器
LoadBalancer  ─── NodePort能力 + 云厂商分配的公网IP/域名

所以实际关系是层层叠加,而不是四个互不相干的平行选项——除了 ExternalName 是个特例,前三种类型是能力递进的关系。
